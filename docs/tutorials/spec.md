# SYSTEM ARCHITECTURE SPECIFICATION: EVOKIT

**Version:** 0.0.1

**Status:** Approved Architectural Baseline

**Paradigm:** Modular, Component-Based Framework for LLM-Guided Evolutionary Algorithm Design

**Target Audience:** System Architects, Core Contributors, and Autonomous Coding Agents

---

## 1. Vision & Core Philosophy

**EvoKit** is an open, production-grade architecture designed to serve as the foundational framework for Automated Heuristic Design (AHD) and LLM-guided program synthesis—analogous to what PyTorch provides for deep learning and Gymnasium/TorchRL provides for reinforcement learning.

Current academic repositories (e.g., EoH, ReEvo, OpenEvolve, LLM4AD) bundle search strategies, execution sandboxes, and problem benchmarks into tight, monolithic scripts. EvoKit decouples these concerns into pluggable, contract-driven components.

### Core Tenets

* **Invariant Core Engine:** The central evolutionary engine manages runtime control flow and telemetry. It remains completely invariant across diverse search paradigms (EoH, ReEvo, OpenEvolve, ShinkaEvolve).
* **3-Pillar Component Architecture:** Complete operational separation between **Population Management**, **Mutation Strategies**, and **Evaluation Services**.
* **Contract-Driven Plugins:** All algorithmic variations operate as dynamic plugins conforming to strict lifecycle interfaces rather than hard-coded logic branches.
* **Hermetic & Secure Execution:** Code generated by LLMs is treated as untrusted and executed exclusively within isolated execution environments via standard protocols (Model Context Protocol / JSON-RPC).
* **Dual-Tier Persistence:** Separation of numerical metrics/metadata (relational database) from concrete code artifacts (filesystem storage), enabling out-of-the-box visualization via existing ecosystem tools (e.g., Optuna Dashboard).

### Component Lifecycle Contract

Every subsystem in EvoKit inherits from a base lifecycle interface (`BaseComponent`):

* **Configuration Ingestion:** Receives an isolated configuration block at runtime.
* **Validation & Setup:** Validates dependencies, resources, and credentials prior to iteration zero.
* **Teardown & Flush:** Gracefully closes network connections, database handles, and container pools upon run termination.

### Data Contracts

* **Individual Entity:** The fundamental unit of evolution. Encapsulates a unique identifier, raw program source code, objective scalar fitness, multidimensional metrics dictionary, execution success flags, and algorithmic metadata (such as parentage IDs, lineage graphs, or natural-language reasoning tokens).
* **Evolution Context:** An immutable state container injected into mutation operators during each generational step. Provides access to current generation index, population read-interfaces, benchmark task specifications, runtime configuration, and the active LLM gateway without exposing global state.

## 4. The Three Pluggable Pillars

### Pillar 1: Population & Archive Management

Responsible for maintaining solution diversity, lineage tracking, and parent selection dynamics.

* **Interface Responsibilities:**
  * Ingest evaluated individuals and determine archive admission/replacement policies.
  * Sample parent candidate sets based on domain criteria (fitness-proportionate, tournament, novelty-based, or island-based).
  * Expose current Pareto fronts or elite candidate solutions for final deployment.

* **Initial Target Implementations:**
  * **Lineage Graph Archive (EoH):** Preserves explicit directed-acyclic-graph structures mapping how textual ideas transition into concrete programs across generations.
  * **Reflection Buffer (ReEvo):** Maintains short-term and long-term execution failure logs paired with synthesized program variants.
  * **MAP-Elites Grid (OpenEvolve):** N-dimensional behavioral tessellation storing high-performing algorithms across orthogonal complexity/heuristic characteristics.

### Pillar 2: Mutation & Search Strategy

Encapsulates all prompt engineering, semantic transformation, and code generation routines.

* **Interface Responsibilities:**
  * Ingest the current `EvolutionContext` and orchestrate LLM interactions to produce candidate program variants.
  * Handle structured output parsing, error recovery, and schema adherence (e.g., separating textual thought chains from executable Python code).

* **Initial Target Implementations:**
  * **EoH Strategy:** Implements the dual Thought-Code evolution mechanism across E1/E2 exploration operators and M1/M2/M3 mutation operators.
  * **ReEvo Strategy:** Implements self-reflective generation loops, analyzing stdout/stderr traces and quantitative sub-metrics from prior failures before producing new code candidates.
  * **Standard Diff Strategy:** Produces targeted patch-style modifications to existing codebases.

### Pillar 3: Evaluation Service (Sandbox Interface)

Executes unverified, LLM-generated source code under hard security, memory, and wall-clock boundaries.

* **Interface Responsibilities:**
  * Ingest raw program strings and problem instances, returning structured evaluation records containing:
    * Scalar fitness score.
    * Boolean validity/execution status.
    * Multi-objective sub-metrics dictionary (e.g., runtime latency, constraint violations, memory footprint).
    * Textual execution feedback (captured stdout, stderr, and explicit failure traces for reflection).

* **Integration Protocols:**
  * Evaluators communicate with sandboxes via standardized JSON-RPC over the **Model Context Protocol (MCP)** or direct container sockets.
  * Physical execution occurs inside isolated, non-root Docker or WebAssembly containers to prevent host-system compromise.

## 5. Benchmark Task & Prompt Abstraction

Following the dataset/environment paradigms established in modern ML libraries:

* **Separation of Splits:** Every benchmark task strictly segregates **Training Instances** (used by the evolutionary loop for rapid fitness assessment) from **Testing Instances** (held out for out-of-distribution generalization testing of final elite algorithms).
* **Domain Prompts as Data:** Benchmark implementations provide prompt templates defining algorithm signatures, functional invariants, and input/output interfaces. Mutation strategies format these templates without embedding domain assumptions into the search logic.
* **Evaluator Coupling:** Benchmark tasks expose deterministic evaluation logic that executes inside the isolated sandbox to compute fitness without human intervention.

## 6. Auxiliary Infrastructure Services

### Unified LLM Gateway

* Provides a provider-agnostic abstraction for language model calls.
* Natively routes between external cloud APIs and local self-hosted inference servers (vLLM running on local GPU infrastructure).
* Standardizes temperature, top-p, seed control, and token budget enforcement across all mutation plugins.

### Dual-Tier Experiment Storage

* **Relational Store:** Tracks trials, timestamps, generational indices, scalar scores, and run configurations using SQLite (default local) or PostgreSQL (distributed scale).
* **Artifact Directory:** Persists every generated algorithm as a standalone Python file on disk using unique trial identifiers.
* **Telemetry Ecosystem Alignment:** Uses database schema compatible with existing visualization engines (specifically `optuna-dashboard`), allowing instant real-time visualization of optimization trajectories without writing custom web dashboards.

## 7. Execution Flow & Lifecycle Sequence

For every evolutionary generation:

1. **Context Construction:** The Orchestrator collects runtime states, active task parameters, and archive references into an `EvolutionContext`.
2. **Search / Mutation:** The configured `MutationStrategy` plugin requests parent references, invokes the `LLMGateway`, extracts structured thought/code pairs, and emits an un-evaluated `Individual`.
3. **Artifact Logging:** The code string is written to physical disk storage with a unique trial identifier.
4. **Sandboxed Evaluation:** The `Evaluator` service passes the code and training instances into the isolated container (via MCP / JSON-RPC). Execution logs, sub-metrics, and scalar fitness are captured.
5. **State Update:**
   * The `PopulationManager` evaluates archive inclusion criteria using fitness and behavioral metrics.
   * The `ExperimentStorage` records execution metadata to the relational database.
6. **Telemetry & Dashboard Sync:** Live metrics are flushed, updating local monitors and external dashboards immediately.

## 8. Implementation Roadmap for Autonomous Coding Agents

Agents executing this architecture must follow this phased sequence:

* **Phase 1: Foundation Scaffolding**
  * Establish the module directory layout.
  * Implement base lifecycle contracts (`BaseComponent`), data structures (`Individual`, `EvolutionContext`), and persistence engines (`ExperimentStorage`).
  * Implement the `LLMGateway` supporting both vLLM local endpoints and cloud endpoints.

* **Phase 2: Benchmark & Sandbox Layer**
  * Implement the abstract `BaseBenchmarkTask` interface with train/test partitioning.
  * Build an initial benchmark instance (e.g., Online Bin Packing or Traveling Salesperson).
  * Build the sandbox evaluator client using isolated subprocessing or Docker container execution with strict timeout controls.

* **Phase 3: The EoH and ReEvo Plugin Stack**
  * Implement the `LineageGraphArchive` to support dual thought-code tracking.
  * Implement `EoHMutationStrategy` leveraging reference implementations under `references/eoh/`.
  * Implement `ReEvoMutationStrategy` with structured textual reflection loops.

* **Phase 4: Orchestration & Configuration Assembly**
  * Implement the clean `EvolutionEngine` coordinating the components.
  * Implement declarative YAML configuration parsing and dynamic class loading via standard library reflection.
  * Build end-to-end integration tests with mock LLM backends to verify execution loops without consuming inference credits.

* **Phase 5: Validation & Ecosystem Integration**
  * Verify real-time experiment tracking via `optuna-dashboard`.
  * Document plugin creation guidelines to enable community contributions of alternative mutation paradigms (e.g., OpenEvolve, ShinkaEvolve).
